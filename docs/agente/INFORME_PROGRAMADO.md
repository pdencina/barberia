## Revalidación y proveedor

**HECHO:** antes y después de generar el informe se releen negocio, preferencia y perfil. Se exige identidad, negocio concreto, admin activo, correo válido y misma revisión/habilitación. El perfil se lee al final de cada validación; el correo utilizado sale exclusivamente de esa lectura final. Si el correo válido cambió, se usa el nuevo; si cambió rol, actividad, negocio o revisión, no se envía. También se comprueba de nuevo fecha/hora: cruzar medianoche durante la generación cancela el envío, y no informa ayer. El informe debe coincidir con el tenant y día reclamados (`src/lib/agente/informe-programado.ts:87-114`).

**HECHO:** el envío reutiliza Resend, render HTML y `EMAIL_FROM` exclusivamente, sin fallback literal ni cuota comercial (`src/lib/agente/informe-diario-email.ts:87-106`). Ausencia de remitente o fallo antes de invocar al proveedor se clasifica fallido. Rechazo explícito de validación/autorización/límite se clasifica fallido; excepción de transporte, respuesta vacía, 5xx o error desconocido se clasifican incierto. El SDK instalado convierte fallos de red en `application_error` (`node_modules/resend/dist/index.js:351-388`); por eso no se equipara cualquier `error` del SDK a rechazo inequívoco. El wrapper manual conserva firma y lanza solo un error genérico si no se confirma aceptación (`src/lib/agente/informe-diario-email.ts:109-112`). No se invocó el proveedor real.

**HECHO:** finalización filtra id del reclamo, tenant, perfil, finalidad y estado procesando, y guarda solo estado, instantes y referencia del proveedor (`src/lib/agente/informe-programado.ts:181-184`). No se inventa un campo de motivo: el SQL 004 solo permite persistir la categoría genérica `fallido`, no una explicación específica. No se guarda texto libre. Fallidos/inciertos/procesando previos nunca se vuelven a reclamar ni se cambian de estado por recuperación. Si falla persistir el resultado, el reclamo se conserva para conciliación y la respuesta lo cuenta incierto. El proveedor puede haber aceptado aunque no se haya podido guardar ese resultado; no se promete entrega exactamente una vez. Pregunta 22 sigue pendiente.

## Límite, simulación y respuesta

**INFERENCIA — propuesta IA5 para Nico:** máximo 20 reclamos nuevos por ejecución, centralizado en `MAX_ENVIOS_POR_EJECUCION` (`src/lib/agente/informe-programado.ts:5-6`). Contar reclamos nuevos, incluso cancelados antes del envío, acota el trabajo con datos; los ya reclamados no gastan ese límite y permiten avanzar en la siguiente pasada. No consume cupo del negocio ni implementa reintentos.
